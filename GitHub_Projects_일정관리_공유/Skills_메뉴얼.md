# 작업 등록

## `/task`

**하는 일**: 지금 바로 진행할 작업을 GitHub Issue로 만들고 `BusDrive_Team_planning` 프로젝트(Nichi72/BusDrive, 번호 3)에 등록한다. Status와 iteration(스프린트)까지 세팅하고 디스코드 팀 채널에 알린다.

**언제 쓰나**: 이번 스프린트에 실제로 착수하는(또는 방금 한) 작업일 때. 나중에 할 일 모음은 `/backlog`를 쓴다.

**`/backlog`와의 차이**:

| | `/task` | `/backlog` |
|---|---|---|
| 담당자 | **필수** — 비어 있으면 등록 안 함 | 지정 안 함 |
| 등록 전 절차 | 제목·담당자·상태·스프린트 **검토 테이블** 확인 | 제목 목록만 확인 |
| Status | 세팅 (`Todo` / `In progress` / `Done`) | 세팅 안 함 |
| 스프린트 | 세팅 (생략하지 않음) | 세팅 안 함 |
| 디스코드 알림 | 보냄 | 안 보냄 |
| 스크린샷 첨부 | 됨 | 안 됨 |

**사용법**:
```
/task 하차 벨이 안 울리는 원인 잡기
```
```
/task Plan/GithubProjectTemp/팀원A 작업 리스트.md 내용을 기반으로 Task 등록
```
- 담당자는 맥락으로 추정한 뒤 검토 테이블에서 고친다. 파일명이 "팀원A 작업 리스트"면 전부 `teammate-a`로 제안한다.
- 작업자 계정: `teammate-a`(팀원A) / `teammate-b`(팀원B) / `teammate-c`(팀원C) / `Nichi72`(세찬)
- 상태 기본값은 `Todo`. 본문에 "진행 중 / 작업 중 / 구현 중" 같은 착수 표현이 있으면 `In progress`로 제안한다.
- 스프린트는 진행 중인 것을 기본값으로 제안한다. 진행 중인 스프린트가 없으면 어느 스프린트인지 물어본다.
- 종료된 스프린트를 지정해도 그대로 세팅하고, 결과 보고에서 종료된 스프린트라고 알려준다.
- Priority와 Size는 건드리지 않는다. 필요하면 보드에서 직접 지정한다.
- 여러 건을 등록하면 디스코드 알림은 한 메시지로 묶어 한 번만 보낸다. 담당자 멘션은 디스코드 ID가 등록된 팀원A·팀원B만 되고, 팀원C·세찬은 이름이 텍스트로 들어간다.

**스크린샷 첨부**: 작업 설명과 함께 스크린샷을 주면 이슈 본문 끝 `## 스크린샷` 절에 붙는다.
- 이미지는 비공개 저장소 `Nichi72/BusDrive-assets`의 `issues/<이슈번호>/` 아래에 올라간다. 팀원은 그 저장소 초대를 수락해야 이슈에서 이미지가 보인다.
- 이미지를 `Nichi72/BusDrive` 본 저장소에 올리지 않는다. LFS 규칙과 충돌하고 전원의 clone 용량이 늘어난다.
- 디스코드 첨부 URL은 약 24시간 뒤 만료되므로 이슈 이미지 링크로 쓰지 않는다.
- 이미지 업로드가 실패해도 이슈 등록은 유지되고, 결과 보고에 실패 사유가 적힌다.

**주의**: 디스코드 웹훅 URL은 환경변수 `BUSDRIVE_DISCORD_WEBHOOK`에 있다. URL 자체가 인증 수단이라 아는 사람은 누구나 채널에 글을 쓸 수 있으니 저장소나 문서에 적지 않는다.

## `/backlog`

**하는 일**: 작성한 백로그 항목들을 GitHub Issue로 만들고 `BusDrive_Team_planning` 프로젝트에 등록한다.

**언제 쓰나**: 할 일·아이디어·발견한 버그를 모아 한 번에 이슈로 쌓아둘 때. 지금 착수하지 않는 것들이다.

**사용법**:
```
/backlog
승객 탑승 애니메이션 추가
정류장 UI 깜빡임 버그
사운드 볼륨 설정 저장
```
- 항목은 줄바꿈/목록 기준으로 분리된다.
- 등록 전 목록을 보여주고 확인받은 뒤 이슈를 생성한다.
- 담당자·스프린트 없이 등록된다. 실제로 착수할 때 보드에서 담당자와 스프린트를 붙인다.

# 작업 일지

## `/todo`

**하는 일**: 이번 작업을 로컬 작업일지에 먼저 적고, 올릴지 물어본 뒤 GitHub 작업일지 이슈에 올린다. 커밋·푸시는 하지 않는다(필요하면 `/git-commit`).

**언제 쓰나**: 작업을 한 덩이 끝내고 일지에 남길 때, 또는 팀이 보드에서 내 진행 상황을 볼 수 있게 일지를 올릴 때.

**사용법**:
```
/todo
/todo 정류장 UI 깜빡임 원인 조사 — 캔버스 재빌드가 매 프레임 일어남
```
- 인자를 주면 그 내용을 적고, 없으면 이 대화에서 실제로 끝낸 작업만 정리해 적는다. 적을 게 없으면 바로 올릴지부터 묻는다.

**로컬 기록**:
- 원본은 로컬 파일이다: `Assets/Docs/TodoList_Plan/박세찬/작업일지_*.md` 중 가장 최근에 수정된 파일의 오늘 날짜 섹션. **06시 전이면 전날 섹션**에 넣는다.
- 그 파일의 마지막 날짜가 오늘보다 3일 넘게 앞서면 새 파일을 만들지 먼저 묻는다.
- 파일에 이미 쓰인 형식(카테고리 묶음 / 한 줄 목록)을 따른다. 작업 하나에 한 줄. 사용자가 적어둔 메모·체크박스는 건드리지 않는다.
- 박세찬이 아닌 사람이 쓰면 일지 폴더와 GitHub 계정을 묻는다.

**GitHub 작업일지 이슈**:
- 사람마다, 스프린트마다 이슈 하나. 제목은 `[작업일지] <이름> — <스프린트 이름>`, 라벨은 `작업일지`, 담당자는 작성자 본인.
- 프로젝트 Status는 `In progress`, iteration은 해당 스프린트. 보드에서 필터로 빼지 않고 작업 중 칸에 계속 보이게 둔다. 스프린트가 끝나면 이슈를 닫는다.
- 이슈가 없으면 새로 만들어 프로젝트에 등록한다. 닫혀 있는 이슈는 다시 열지 않고 물어본다.
- 스프린트는 오늘이 들어가는 것을 쓴다. 오늘이 어느 스프린트에도 안 들어가면 추측하지 않고 물어본다.
- 본문에는 그 스프린트 기간에 드는 일지 파일들이 **원문 그대로**, 최신 날짜가 위로 오게 들어간다.
- 일지 속 이미지(마크다운 `![]()`, Obsidian `![[...]]`)는 `Nichi72/BusDrive-assets`에 올리고 이슈 본문의 링크만 바꾼다. 로컬 파일은 바꾸지 않는다.

**주의**: 올릴 때마다 이슈 본문을 로컬 일지로 **통째로 교체**한다. 웹에서 이슈 본문을 직접 고친 내용은 사라진다. 올리기 전에 사라지는 줄을 보여주고 확인받으니 그때 확인한다. 고칠 것은 로컬 파일에서 고친다.

**`/end`와의 차이**: 둘 다 같은 로컬 작업일지에 적는다. `/todo`는 GitHub 이슈에 올리는 것까지, `/end`는 세션 이름을 바꾸는 것까지 한다.

# Git

## `/git-branch`

**하는 일**: BusDrive 브랜치 컨벤션에 맞춰 git 브랜치를 만든다. 작업 설명을 주면 성격(feature/fix/chore/refactor/docs)을 판단해 접두어를 붙여 생성·전환한다.

**언제 쓰나**: 새 작업을 시작하며 브랜치를 딸 때.

**사용법**:
```
/git-branch 승객이 1일차 손님만 나오는 버그
```
- 버그 → `fix/`, 새 기능 → `feature/`, 작고 잡다함 → `chore/misc` 식으로 알아서 판단.
- 판단 기준: "독립적으로 main에 넣고 뺄 만큼 큰 작업인가?"
- 접두어 뒤 이름은 영어 kebab-case로 짓는다 (예: `fix/passenger-day-spawn`). 작업자 이름은 넣지 않는다.
- 기본은 `main`에서 딴다. 현재 브랜치가 `main`이 아니면 어디서 딸지 확인한다. `chore/misc`처럼 이미 있는 브랜치는 새로 만들지 않고 전환만 한다.
- 관련 규칙 문서: Git 브랜치 전략 (BusDrive 저장소 내부 문서)

## `/git-commit`

**하는 일**: 스테이징된 변경(없으면 전체)을 읽어 `타입: 한국어 요약` 형식의 메시지를 쓰고 커밋한다.

**언제 쓰나**: 작업을 끊어 커밋할 때. 메시지 형식을 매번 떠올리지 않아도 된다.

**사용법**:
```
/git-commit
```
- 타입은 `feat`(새 기능) / `fix`(버그 수정) / `refactor`(동작 변경 없는 구조 개선) / `docs`(문서) / `chore`(잡다한 정리·설정) 중 주된 목적 하나로 고른다.
- 제목은 한국어 50자 이내, 마침표 없이 명사형. 변경 항목이 여러 개면 본문에 `-` 목록을 붙인다.
- 성격이 다른 변경이 섞여 있으면 커밋을 나누자고 먼저 제안한다.
- **push는 하지 않는다.** 요청해야 한다.
- `main`에서 바로 커밋하려 하면 브랜치 전략을 한 번 상기시킨다. 그대로 원하면 진행한다.
- 관련 규칙 문서: Git 커밋 컨벤션 (BusDrive 저장소 내부 문서)

**주의**: `amend`나 force 같은 히스토리 변경은 이 스킬 범위가 아니다.

# 캐릭터 · 대사

두 스킬은 `/voice` → `/dialogue` 순서로 쓴다. 말투 명세 없이 대사를 만들면 캐릭터가 전부 같은 톤이 된다.

## `/voice`

**하는 일**: 캐릭터 문서의 `## 예시 대사`를 읽어 말투를 역산해 같은 문서의 `## 말투 명세` 섹션에 기록한다.

**언제 쓰나**: 캐릭터 예시 대사를 채운 뒤, 그 캐릭터의 대사를 생성하기 전에.

**사용법**:
```
/voice 곽춘식
```
- 대상 문서: `Assets/Docs/Story/1_Characters/Passengers/{이름}.md` 또는 `.../StoryNpcs/{이름}.md`. `1_Characters/` 아래를 이름으로 검색해 찾고, 없으면 만들지 않고 알린다.
- 9개 축의 정의는 `Assets/Docs/Story/2_Style/말투_축.md`에 있다.
- **프로필에서 말투를 추론하지 않는다.** "70대 남성이니까 하게체를 쓸 것이다" 같은 추론은 금지다. 캐릭터가 전부 스테레오타입으로 수렴한다. 근거는 예시 대사 문장뿐이고, 근거가 없는 축은 `근거 없음 — 예시 필요`로 남는다.
- 채워진 예시 슬롯이 3개 미만이면 추출하지 않고 어떤 슬롯을 채워야 하는지 알려준다.
- 손으로 고친 항목 끝에 `[고정]`을 붙여두면 덮어쓰지 않는다. 새 추출 결과와 충돌하면 보고에 표시만 한다.
- `## 프로필`과 `## 예시 대사`는 읽기만 하고 수정하지 않는다.

**보고 내용**: 채워진/빈 슬롯 목록, 근거 없이 남긴 축, `[고정]` 충돌, 먼저 채우면 좋을 슬롯 추천.

## `/dialogue`

**하는 일**: 말투 명세를 근거로 인게임 대화문 `.yarn`을 생성한다. 생성 직후 말투 자가점검 10항목을 돌린다.

**언제 쓰나**: 승객 대화나 스토리 씬 대사를 만들 때. 인자는 캐릭터 이름 또는 씬 이름이다.

**사용법**:
```
/dialogue 곽춘식
/dialogue 프롤로그-사무실-아침
```
- 승객 출력 경로: `Assets/0.MyAsset/Scripts/Dialogue/Yarns/Passengers/P_Fixed_{Id}.yarn`, 구조는 `Assets/Docs/Story/2_Style/승객_대화_템플릿.md`의 비트 대응표를 따른다.
- 스토리 씬 출력 경로: `Assets/0.MyAsset/Scripts/Dialogue/Yarns/{씬}.yarn`, 구조는 `Assets/Docs/Story/3_Scenes/{씬}.md` 씬 카드를 따른다. 씬 카드가 없으면 만들지 않고 먼저 작성하라고 알린다.
- **말투 명세와 예시 대사를 벗어난 대사를 쓰지 않는다.** 명세에 `근거 없음`인 축이 있으면 그 축이 필요한 대사는 생성하지 않고 물어본다. 예시 대사와 말투 명세가 충돌하면 예시가 이긴다.
- 말투 명세가 `_아직 추출되지 않음_`이면 생성하지 않고 `/voice {이름}`을 먼저 돌리라고 알린다.
- 기존 `.yarn`이 있으면 먼저 읽고, 노드 `position:` 값과 주석 처리된 노드를 보존하며, **덮어쓰기 전에 무엇이 바뀌는지 보여주고 확인받는다.**
- 자가점검에서 표정 지시문(`(웃으며)` 등)은 무조건 제거한다. 표정 리깅이 없어서 표정 연출을 못 한다.

- 소설 원문(`Assets/Docs/Story/4_Source/`)은 읽지 않는다. 필요한 사실이 `0_Lore/`·`1_Characters/`에 정리돼 있지 않으면 생성을 멈추고 알린다.

**주의**: 캐릭터 문서(말투 명세 포함)는 고치지 않는다. 그건 `/voice`의 일이다.

# 코드 리뷰

## `/unity-code-review`

**하는 일**: C# 코드·프리팹·씬 변경을 검증하고 리뷰한다. 일반적인 C# 리뷰 기준 대신 **이 프로젝트의 기존 구조를 기준선으로 삼고, 그 기준선을 나쁜 방향으로 미는 변경**을 잡는다.

**언제 쓰나**: 기능을 새로 구현했거나 크게 고친 뒤, 구조가 복잡해지는 것 같을 때, 병합 충돌이나 성능이 걱정될 때, PR·브랜치를 검토할 때. Unity 기능을 크게 구현·수정한 직후에는 Claude가 먼저 제안하기도 한다.

**사용법**:
```
/unity-code-review
/unity-code-review 승객 스폰 쪽 구조 괜찮은지 봐줘
```
- **읽기 전용이 기본이다.** 수정까지 요청하지 않으면 코드·씬·프리팹을 바꾸지 않는다. 플레이 모드도 명시적으로 허용할 때만 실행한다.
- 변경이 크면 리뷰 범위를 좁힐지 먼저 묻는다.

**보는 것**:
- **독립성과 결합도** — 한 클래스가 너무 많은 책임을 갖는지, UI가 게임 규칙을 갖는지, 이벤트 구독·해제가 대칭인지, ScriptableObject에 런타임 값을 쓰는지.
- **싱글톤** — 기존 싱글톤을 쓰는 것은 지적하지 않는다. 새로 추가하거나 새 레이어까지 퍼뜨릴 때 지적한다.
- **복잡도** — 새 타입·인터페이스·Manager가 현재 요구사항으로 정당화되는지. `적정` / `주의` / `과설계`로 판정한다.
- **협업 병합성** — 중앙 씬 수정 최소화, 프리팹 단위 완결성, 네임스페이스 선언. `.prefab`/`.unity`는 Git LFS라 병합이 안 되므로 새 기능은 새 프리팹·새 `.asset`·새 스크립트로 만들었는지 본다.
- **가독성** — C# 주석 컨벤션, 네이밍 컨벤션 (BusDrive 저장소 내부 문서), Inspector 필드의 `[Header]`/`[Tooltip]`.
- **런타임 품질** — `Update` 안의 `Find*`/`GetComponent`/LINQ/할당, 조회 패턴에 안 맞는 컬렉션, 풀링 부재, 초기화 순서 가정.

**보고 내용**: 결론(통과 / 조건부 통과 / 수정 권장 / 위험), 구조 요약, 복잡도 판정, 심각도(`P0`~`P3`)순 발견 사항 표, 좋은 점, 검증 결과와 검증하지 못한 범위, 다음 조치. 지적마다 파일·줄 번호가 붙고, 확인하지 못한 것은 "확인 필요"로 분류된다.

**함께 들어 있는 파일** (`.claude/skills/unity-code-review/`):
- `references/project-baseline.md` — 기준선 수치(싱글톤 수, 네임스페이스 비율 등). 리뷰 전에 읽는다.
- `references/unity-runtime-checklist.md` — 성능·자료구조·수명주기 세부 체크리스트.
- `scripts/scan_architecture.py` — 기준선 수치를 다시 재는 스크립트.

**주의**: Unity가 꺼져 있으면 MCP 대신 Roslyn으로 오프라인 컴파일 검증을 한다. 프리팹 중첩·직렬화 필드 연결처럼 에디터 실행이 필요한 항목은 "검증하지 못한 범위"로 보고된다.

# 진행 방식

## `/brainstorm`

**하는 일**: 요구사항을 바로 구현하지 않고, 이해한 내용을 먼저 검토받은 뒤 선택형 질문으로 구체화한다.

**언제 쓰나**: 아직 방향이 덜 정해진 기능·설계를 같이 다듬고 싶을 때. 바로 코드부터 짜지 않게 하고 싶을 때.

**사용법**:
```
/brainstorm 승객 감정 시스템을 넣고 싶은데 어떻게 할지 같이 고민하자
```
- 맨 먼저 진행 방식을 묻는다: 결정 지점마다 선택지 UI로 묻는 **선택형 질문 모드**, 또는 글로 묻고 답하는 **대화형 모드**. 중간에 "그냥 물어봐" / "선택지로 줘"라고 하면 바뀐다.
- 흐름: 이해한 내용 검토 → 접근 방식 2~4개와 장단점 제시, 결정 지점마다 한 번에 하나씩 질문 → 합의 내용 요약 후 "이대로 구현 시작할까?" 확인.
- "구현 시작"을 고르기 전까지는 코드를 작성하지 않는다.

**주의**: 예전에는 개인 스킬(`~/.claude/`)이었고 2026-09-22에 저장소로 옮겨 커밋했다. 개인 폴더에 옛 사본이 남아 있으면 지우는 게 좋다. 저장소 쪽이 정본이다.

## `/end`

**하는 일**: 이번 세션에서 한 작업을 작업일지에 짧게 남기고, 세션 이름을 `완) <세션 요약>`으로 바꾼다.

**언제 쓰나**: 세션을 끝낼 때. 커밋·푸시는 하지 않는다(필요하면 `/git-commit`).

**사용법**:
```
/end
/end 디버그 오버레이 일차 표시
```
- 인자를 주면 그게 세션 이름이 되고, 없으면 이번 세션 핵심 작업을 20자 안팎 명사구로 만든다.
- 기록 위치: `Assets/Docs/TodoList_Plan/박세찬/작업일지_*.md` 중 가장 최근에 수정된 파일의 오늘 날짜 섹션. **06시 전이면 전날 섹션**에 넣는다(새벽 작업은 전날로 친다).
- 그 파일의 마지막 날짜 섹션이 오늘보다 3일 넘게 앞서면 새 파일을 만들지 먼저 묻는다.
- 조사만 하고 코드를 안 바꾼 세션이면 알아낸 결론을 한 줄로 남긴다.
- 이 대화에서 실제로 끝낸 작업만 적는다. 워킹 트리에는 다른 세션의 미커밋 변경도 섞여 있어서 `git status`를 통째로 옮기지 않는다.
- 작업 하나에 한 줄, 짧은 명사형으로. 사용자가 적어둔 메모·체크박스는 건드리지 않는다.
- 이 스킬은 모델이 알아서 쓰지 않는다(`disable-model-invocation`). 직접 `/end`를 불러야 한다.

**주의**: 세션 이름 변경은 Claude Code 내부 세션 기록 파일(`~/.claude/projects/<프로젝트>/<세션ID>.jsonl`)에 제목 한 줄을 덧붙이는 방식이다. 버전이 바뀌면 안 먹힐 수 있다. 이름이 안 바뀌면 `/rename 완) <세션 요약>`을 직접 입력하면 된다.
