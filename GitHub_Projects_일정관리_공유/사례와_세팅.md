## 1. 무엇을 하는 구성인가

일정은 GitHub Projects 보드 하나에 모은다. 보드에 올리는 일은 사람이 웹에서 클릭하지 않고, Claude Code 대화창에서 슬래시 명령으로 한다.

| 명령         | 하는 일                                                                                      |
| ------------ | -------------------------------------------------------------------------------------------- |
| `/task`    | 지금 할 작업을 이슈로 만들고, 담당자·상태·스프린트를 붙여 보드에 올린 뒤 디스코드에 알린다 |
| `/backlog` | 나중에 할 일 여러 개를 한 번에 이슈로 만들어 보드에 쌓는다                                   |
| `/todo`    | 작업일지를 로컬 파일에 쓰고, 스프린트별 작업일지 이슈에 올린다                               |

`/task` 한 번이 대신해 주는 일은 다음과 같다. 웹에서 하면 이슈 하나에 화면을 서너 번 오가야 하는 작업이다.

```
작업 설명 입력
  → 검토 표 (제목 / 담당자 / 상태 / 스프린트) 확인
  → 이슈 생성 + 담당자 지정
  → 프로젝트 보드에 등록
  → Status, 스프린트 세팅
  → 스크린샷이 있으면 이슈 본문에 첨부
  → 디스코드 채널에 담당자 호명
```

쓰는 도구는 세 가지다.

- **GitHub Projects**: 보드, 스프린트(iteration 필드), 사람별 뷰
- **GitHub CLI (`gh`)**: 이슈와 보드를 명령으로 조작한다. Claude Code가 이 명령을 대신 실행한다
- **Claude Code 스킬**: 팀 규칙(담당자 필수, 등록 전 확인 등)을 적어 둔 절차 문서. 저장소 `.claude/skills/`에 커밋해 두면 팀 전체가 같은 절차를 쓴다

별도 서버나 GitHub Actions는 쓰지 않는다. 사람이 명령을 부를 때만 동작한다.

### 보드 구성

**필드**

| 필드      | 값                                             | 누가 채우나                               |
| --------- | ---------------------------------------------- | ----------------------------------------- |
| Status    | Todo / In progress / 작업 완료(확인 전) / Done | `/task`가 세팅, 이후 보드에서 직접 이동 |
| iteration | 스프린트                                       | `/task`가 세팅                          |
| Assignees | 담당자                                         | `/task`가 세팅 (필수)                   |
| Priority  | P0 / P1 / P2                                   | 보드에서 직접                             |
| Size      | XS ~ XL                                        | 보드에서 직접                             |
| Milestone | 큰 목표 3개                                    | 보드에서 직접                             |

**뷰** — 10개를 쓴다.

| 뷰                | 형태   | 필터                              |
| ----------------- | ------ | --------------------------------- |
| Backlog           | 표     | 없음                              |
| Current iteration | 보드   | `iteration:@current`            |
| Sprint Board      | 보드   | 없음                              |
| 로드맵 2개        | 로드맵 | 특정 스프린트                     |
| 마일스톤별 보드   | 보드   | 특정 스프린트, Milestone으로 묶음 |
| 사람별 뷰 4개     | 보드   | `assignee:계정`                 |

### 작업 등록: `/task`와 `/backlog`

|                  | `/task`                         | `/backlog`                        |
| ---------------- | --------------------------------- | ----------------------------------- |
| 쓰는 때          | 이번 스프린트에 착수하는 작업     | 나중에 할 일, 아이디어, 발견한 버그 |
| 담당자           | 필수. 비어 있으면 등록하지 않는다 | 지정하지 않는다                     |
| 등록 전          | 검토 표를 보여 주고 확인받는다    | 제목 목록을 보여 주고 확인받는다    |
| Status·스프린트 | 세팅한다                          | 세팅하지 않는다                     |
| 디스코드 알림    | 보낸다                            | 보내지 않는다                       |
| 스크린샷         | 붙일 수 있다                      | 붙일 수 없다                        |

`/task`를 부르면 Claude가 이런 표를 먼저 보여 준다(예시).

```
/task 하차 벨이 안 울리는 원인 잡기

| # | 제목                         | 담당자  | 상태 | iteration | 본문요약       |
|---|------------------------------|---------|------|-----------|----------------|
| 1 | 하차 벨이 안 울리는 원인 잡기 | (미지정) | Todo | Sprint 13 | (이미지 1장)   |

담당자를 지정해 주세요.
```

담당자는 파일 이름이나 대화 맥락에 힌트가 있으면 Claude가 추정해 채우고, 없으면 비워 둔다. 상태는 기본 `Todo`이고, 본문에 "진행 중" 같은 표현이 있으면 `In progress`로 제안한다. 사람이 표를 고치고 확인한 뒤에야 이슈가 만들어진다.

### 디스코드 알림

알림은 두 겹이다.

1. **저장소 웹훅** — 이슈가 생기거나 댓글이 달리면 GitHub가 디스코드 채널에 카드를 자동으로 올린다.
2. **`/task`의 메시지** — 그 위에 담당자를 `@멘션`으로 호명하는 메시지를 한 번 더 보낸다. 여러 건을 등록하면 한 메시지로 묶는다.

> **[캡처 6 자리]** 디스코드 채널 — GitHub 카드와 담당자 멘션 메시지가 나란히 보이게

### 스크린샷 첨부

GitHub API로는 이슈에 이미지를 직접 올릴 수 없다. 그래서 이미지 보관 전용 비공개 저장소를 따로 두고, `issues/<이슈번호>/` 아래에 올린 뒤 이슈 본문에 링크로 붙인다.

- 본 저장소에 올리지 않는다. 전원의 clone 용량이 늘기 때문이다.
- 디스코드 첨부 URL은 약 24시간 뒤 만료되므로 이슈 링크로 쓰지 않는다.
- 팀원은 이미지 저장소의 초대를 수락해야 이슈에서 이미지가 보인다.

### 작업일지: `/todo`

작업일지는 로컬 마크다운 파일이 원본이고, 팀이 보드에서 볼 수 있게 이슈로 올린다.

- **사람마다, 스프린트마다 이슈 하나.** 제목은 `[작업일지] <이름> — <스프린트 이름>`, 라벨은 `작업일지`.
- 하루치를 댓글로 달지 않고 **이슈 본문을 계속 교체**한다. 올릴 때마다 그 스프린트 기간의 로컬 일지 파일을 최신 날짜가 위로 오게 이어 붙여 본문으로 넣는다.
- Status는 `In progress`로 두고 보드에서 필터로 빼지 않는다. 작업 중 칸에 계속 보이게 하기 위해서다.
- 스프린트가 끝나면 이슈를 닫는다.
- 올리기 전에 "사라지는 줄"을 보여 준다. 웹에서 이슈 본문을 직접 고친 내용은 다음에 올릴 때 사라지므로, 고칠 것은 로컬 파일에서 고친다.

![작업일지 이슈](Image/07_worklog_issue.webp)
*작업일지 이슈. 라벨 `작업일지`, Status `In progress`, 본문은 날짜별 일지다.*

## 3. 세팅 방법

갖춰야 할 것은 여섯 단계다. 단계마다 무엇을 갖추는지 적고, 그 아래에 Claude Code에 그대로 붙여 넣을 요청문을 두었다. `<...>` 자리만 자기 팀 값으로 바꾸면 된다. 사람이 직접 하는 것은 로그인, 비밀값 다루기, 웹에서만 되는 설정 몇 가지뿐이다.

| 단계 | 갖추는 것 |
|---|---|
| 1 | 작업 환경 — GitHub CLI 로그인 |
| 2 | 프로젝트 보드 — 필드, 스프린트, 뷰 |
| 3 | 작업일지 라벨과 이미지 저장소 |
| 4 | 디스코드 알림 연결 |
| 5 | 작업 등록·작업일지 스킬 |
| 6 | 동작 확인 |

> 아래 요청문은 우리가 손으로 만들어 온 구성을 말로 옮긴 것이다. 필요한 GitHub API가 있는 것은 확인했지만(2026-10-02), 빈 저장소에서 처음부터 돌려 본 것은 아니다. Claude가 막히면 [4절의 함정](#4-우리가-겪은-함정)을 먼저 본다.

### 준비

1. **이 폴더(`GitHub_Projects_일정관리_공유/`)를 통째로 자기 저장소에 복사한다.** 위치는 아무 곳이나 된다(예: `Docs/`). Claude가 이 문서와 스킬 템플릿을 읽고 따라 하기 때문이다. 아래 요청문은 `Docs/`에 넣었다고 보고 썼으니, 다른 곳에 넣었으면 경로만 바꾼다.
2. **GitHub CLI를 설치한다.** [https://cli.github.com/](https://cli.github.com/). 설치도 Claude에게 시킬 수 있다(1단계).
3. **아래 값을 정해 둔다.** 요청문에 넣을 값이다.

| 정할 것                     | 예시                                                  |
| --------------------------- | ----------------------------------------------------- |
| 저장소                      | `my-team/my-game`                                   |
| 보드 이름                   | `MyGame_Team_planning`                              |
| 스프린트 길이와 첫 시작일   | 2주, 2026-10-05                                       |
| 팀원의 GitHub 계정과 이름   | `github-login-a` 홍길동, `github-login-b` 김철수  |
| 쓸 기능                     | 디스코드 알림 / 스크린샷 첨부 / 작업일지 중 필요한 것 |
| 작업일지 폴더               | `Docs/Worklog`                                      |
| 디스코드 웹훅 환경변수 이름 | `MYTEAM_DISCORD_WEBHOOK`                            |

### 사람이 직접 하는 것

Claude가 대신할 수 없는 일은 여섯 가지다. 방법은 해당 단계에 적었다.

| 할 일                      | 직접 하는 이유                       | 언제          | 누가                     |
| -------------------------- | ------------------------------------ | ------------- | ------------------------ |
| GitHub CLI 로그인          | 브라우저에서 본인 인증을 한다        | 1단계    | 팀원 각자                |
| 보드 Workflows 켜기        | 켜는 API가 없다                      | 2단계 뒤 | 한 사람                  |
| 이미지 저장소 초대 수락    | 초대받은 본인만 할 수 있다           | 3단계 뒤 | 팀원 각자                |
| 디스코드 웹훅 만들기       | 디스코드 앱 안에서만 된다            | 4단계 전 | 한 사람                  |
| 웹훅 URL을 환경변수에 넣기 | 비밀값이라 대화창에 붙여 넣지 않는다 | 4단계 전 | `/task`를 쓸 사람 각자 |
| 팀원 디스코드 ID 모으기    | 디스코드 앱 안에서만 보인다          | 5단계 전 | 한 사람                  |

### 1단계. 작업 환경 준비 — GitHub CLI 로그인

**갖출 것**: Claude가 `gh` 명령으로 이슈와 보드를 다룰 수 있는 상태. `gh`가 keyring 방식으로 로그인돼 있고 토큰에 `repo`·`project` 범위가 있어야 한다.

Claude에게 이렇게 말한다.

```
Docs/GitHub_Projects_일정관리_공유 폴더의 사례와_세팅.md 와 스킬_템플릿/README.md 를 읽어줘.
우리 저장소 <주인>/<저장소> 에 이 문서의 일정 관리 환경을 만들 거야.

먼저 내 환경을 점검해줘.
- gh CLI가 설치돼 있는지, 버전이 몇인지
- gh 로그인이 keyring 방식으로 돼 있는지
- 토큰에 repo 와 project 범위가 있는지
- 환경변수 GITHUB_TOKEN 이 남아 있는지

빠진 게 있으면 내가 뭘 해야 하는지 알려주고, 네가 할 수 있는 건 물어본 뒤 해줘.
```

**직접 할 일 — 로그인.** Claude가 로그인이 필요하다고 하면 터미널에서 실행한다.

```bash
gh auth login               # GitHub.com → HTTPS → 브라우저로 로그인
gh auth refresh -s project  # 프로젝트 보드를 조작할 권한 추가
```

환경변수 `GITHUB_TOKEN`은 만들지 않는다. 남아 있으면 Claude에게 지워 달라고 한다. 이유는 [함정 1](#4-우리가-겪은-함정)에 있다.

### 2단계. 프로젝트 보드 구축 — 필드, 스프린트, 뷰

**갖출 것**: 저장소에 연결된 보드 하나. Status 칸, 스프린트 필드와 진행 중인 스프린트, 현재 스프린트·Backlog·팀원별 뷰가 있어야 한다.

Claude에게 이렇게 말한다.

```
<주인>/<저장소> 용 GitHub Projects 보드를 만들어줘.

- 이름: <보드 이름>, 비공개, 저장소에 연결
- Status 칸: Todo / In progress / Done
- 스프린트 필드: 이름 Iteration, 타입 Iteration, <첫 시작일>부터 <N>주 단위, 첫 스프린트 이름은 Sprint 1
- Priority 필드(P0 / P1 / P2), Size 필드(XS / S / M / L / XL)
- 뷰 세 가지
  - 현재 스프린트 보드: 필터 iteration:@current, Status로 칸을 나눔
  - Backlog: 표 형태, 필터 없음
  - 팀원별 보드: 팀원마다 하나씩, 필터 assignee:<계정>. 팀원은 <계정 목록>

다 만든 뒤 프로젝트 번호와 필드 목록을 조회해서 보여줘.
API로 안 되는 게 있으면 건너뛰지 말고, 웹에서 내가 어떻게 하면 되는지 알려줘.
```

끝나면 Claude가 알려 주는 **프로젝트 번호**를 적어 둔다. 보드 주소 `.../projects/N`의 N이다.

스킬이 실제로 요구하는 것은 Status의 `Todo`·`In progress`·`Done` 세 칸, Iteration 타입 스프린트 필드, 담당자 세 가지다. Priority·Size와 뷰는 없어도 스킬이 동작한다.

**직접 할 일 — Workflows 켜기.** 보드 오른쪽 위 **⋯ → Workflows**에서 필요한 것을 켠다. `Auto-add to project`는 대상 저장소를 고르고 저장해야 동작한다.

**웹에서 확인할 화면.** 보드 **⋯ → Settings**의 스프린트 필드에 진행 중인 스프린트가 하나 있어야 한다.

![스프린트 필드 설정 화면](Image/08_iteration_field_settings.webp)
*스프린트 필드 설정 화면. 이 화면처럼 Active가 0이면 진행 중인 스프린트가 없는 상태이고, `/task`가 매번 어느 스프린트인지 묻는다.*

### 3단계. 작업일지 라벨과 이미지 저장소 구축

**갖출 것**: 작업일지 이슈에 붙일 `작업일지` 라벨, 그리고 이슈에 붙는 스크린샷을 보관할 비공개 저장소. `/todo`를 안 쓰면 라벨 줄을, 스크린샷 첨부를 안 쓰면 이미지 저장소 줄을 뺀다.

Claude에게 이렇게 말한다.

```
<주인>/<저장소> 에 "작업일지" 라벨을 만들어줘. 설명은 "사람별·스프린트별 작업 일지".

이슈 첨부 이미지를 보관할 비공개 저장소 <주인>/<저장소>-assets 도 만들어줘.
README를 넣어서 기본 브랜치가 main 이 되게 하고, 팀원 <계정 목록> 을 collaborator로 초대해줘.
```

**직접 할 일 — 초대 수락.** 팀원 각자 GitHub 알림이나 메일에서 초대를 수락한다. 수락하지 않으면 그 사람 화면에서만 이슈의 이미지가 깨져 보인다. 누가 아직 안 했는지는 Claude에게 물으면 된다.

```
이미지 저장소 초대를 아직 수락하지 않은 사람이 누군지 알려줘.
```

### 4단계. 디스코드 알림 연결

**갖출 것**: 이슈가 생기면 디스코드 채널에 카드가 자동으로 뜨는 연결, 그리고 `/task`가 담당자를 호명할 때 쓰는 웹훅. 디스코드 알림을 쓸 팀만 한다.

먼저 직접 할 일 두 가지를 끝낸다.

**직접 할 일 ① 웹훅 만들기.** 디스코드에서 알림받을 채널의 설정 → **연동** → **웹후크** → **새 웹후크** → **웹후크 URL 복사**.

**직접 할 일 ② 환경변수에 넣기.** 터미널에서 직접 실행한다. 설정한 뒤 터미널과 Claude Code를 다시 시작한다.

```powershell
# Windows PowerShell
[Environment]::SetEnvironmentVariable('MYTEAM_DISCORD_WEBHOOK', '<웹훅 URL>', 'User')
```

```bash
# macOS / Linux — ~/.zshrc 또는 ~/.bashrc 에 추가
export MYTEAM_DISCORD_WEBHOOK='<웹훅 URL>'
```

웹훅 URL은 그 자체가 인증 수단이다. 아는 사람은 누구나 그 채널에 글을 쓸 수 있으니 대화창·저장소·문서·스킬 파일에 적지 않는다.

그다음 Claude에게 시킨다.

```
환경변수 MYTEAM_DISCORD_WEBHOOK 에 디스코드 웹훅 URL을 넣어 뒀어. URL 값은 화면에 출력하지 말고 써줘.

1) 이 URL 끝에 /github 를 붙여서 <주인>/<저장소> 저장소의 웹훅으로 등록해줘.
   content type은 json, 이벤트는 issues 와 issue_comment 만.
2) 환경변수의 URL로 테스트 메시지를 하나 보내서 HTTP 204가 오는지 확인해줘.
```

1번은 이슈가 생기거나 댓글이 달릴 때 채널에 카드가 자동으로 뜨게 하는 설정이고, 2번은 `/task`가 담당자를 호명할 때 쓰는 경로를 확인하는 것이다.

### 5단계. 작업 등록·작업일지 스킬 설치

**갖출 것**: 자기 팀 값이 들어간 `/task`, `/backlog`, `/todo` 스킬. 저장소 `.claude/skills/`에 들어가 팀 전체가 같이 쓴다.

**직접 할 일 — 팀원 디스코드 ID 모으기.** 디스코드 설정 → 고급 → **개발자 모드**를 켠 뒤, 사용자를 우클릭 → **사용자 ID 복사**. 숫자 18자리 안팎이다. ID를 모르는 사람은 멘션 대신 이름이 글자로 들어간다.

Claude에게 이렇게 말한다.

```
Docs/GitHub_Projects_일정관리_공유/스킬_템플릿 의 task, backlog, todo 스킬을 .claude/skills/ 에 설치해줘.

- 저장소: <주인>/<저장소>
- 보드: <보드 이름>, 프로젝트 번호 <N>
- 스프린트 필드 이름: Iteration
- 이미지 저장소: <저장소>-assets
- 디스코드 웹훅 환경변수: MYTEAM_DISCORD_WEBHOOK
- 작업일지 폴더: Docs/Worklog (양식도 Docs/Worklog/_Templates/작업일지.md 로 복사)
- 팀원: github-login-a 홍길동 (디스코드 123456789012345678), github-login-b 김철수 (디스코드 ID 모름)

우리는 <안 쓰는 기능>은 안 쓰니까 그 단계는 스킬에서 빼줘.
설치한 뒤 {{ 가 남은 곳이 없는지 확인하고, 바꾼 값을 표로 보여줘.
```

설치 후 Claude Code를 다시 시작한다. `/task`, `/backlog`, `/todo`가 명령 목록에 뜨면 된 것이다. `.claude/skills/`를 커밋해 팀과 공유한다.

스킬은 평범한 마크다운 문서라서, 팀 규칙에 맞게 고치는 것도 말로 시키면 된다. 예: "`/task`의 Status 칸에 `검토 중`을 추가해줘."

### 6단계. 동작 확인

**확인할 것**: 이슈 등록, 보드 세팅, 디스코드 알림, 스크린샷 첨부, 작업일지 올리기가 전부 이어지는지. 하나씩 돌려 보고 결과를 눈으로 확인한다.

1. `/backlog 테스트 항목` — 이슈가 생기고 보드에 올라오는지 본다.
2. `/task 테스트 작업` — 검토 표가 나오는지, 등록 후 보드에서 담당자·Status·스프린트가 들어갔는지, 디스코드에 카드와 멘션이 왔는지 본다.
3. 스크린샷을 하나 붙여 `/task`를 한 번 더 — 이슈 본문에 이미지가 보이는지, **다른 팀원 계정에서도 보이는지** 본다.
4. `/todo 테스트` — 로컬 일지에 한 줄이 들어가고, 올리겠다고 답하면 작업일지 이슈가 만들어지는지 본다.

끝나면 정리한다.

```
방금 테스트로 만든 이슈들을 닫아줘.
```

### 팀원이 합류할 때

보드와 스킬은 이미 있으므로, 새 팀원은 자기 환경만 맞추면 된다. 저장소를 받은 뒤 Claude Code에 이렇게 말한다.

```
이 저장소는 GitHub Projects 일정 관리 스킬(/task, /backlog, /todo)을 써.
내 환경에서 쓸 수 있는지 점검해줘: gh 로그인과 project 범위, 환경변수 GITHUB_TOKEN,
환경변수 MYTEAM_DISCORD_WEBHOOK, 이미지 저장소 접근 권한.
```

기존 팀원 쪽에서는 새 팀원을 등록한다.

```
새 팀원 <계정> <이름> (디스코드 <ID>) 을 task 와 todo 스킬의 팀원 목록에 넣어줘.
이미지 저장소에 초대하고, 보드에 이 사람용 뷰(assignee:<계정>)도 만들어줘.
```

### 스프린트가 바뀔 때

진행 중인 스프린트가 보드에 없으면 `/task`가 매번 어느 스프린트인지 묻고, 현재 스프린트 뷰가 비어 보인다. 스프린트가 끝나기 전에 다음 것을 등록한다.

```
보드에 다음 스프린트를 등록해줘. 이름은 Sprint 2, <시작일>부터 2주.
```

## 4. 우리가 겪은 함정

**1. `GITHUB_TOKEN` 환경변수가 로그인을 덮어쓴다.**
`gh`는 keyring 로그인보다 환경변수 `GITHUB_TOKEN`을 우선한다. 예전에 넣어 둔 토큰이 만료되면, `gh auth login`이 멀쩡해도 모든 명령이 `HTTP 401: Bad credentials`로 실패한다. `gh auth status`에 "The token in GITHUB_TOKEN is invalid"가 보이면 이 경우다. 환경변수를 지우면 해결된다.

```powershell
[Environment]::SetEnvironmentVariable('GITHUB_TOKEN', $null, 'User')   # Windows, 영구 삭제
```

**2. 토큰에 `project` 범위가 없으면 보드 명령만 실패한다.**
이슈는 만들어지는데 보드 등록에서 막힌다. `gh auth refresh -s project`로 추가한다.

**3. 스프린트 ID는 GraphQL로만 조회된다.**
`gh project field-list`는 스프린트 필드의 ID까지만 준다. 개별 스프린트의 ID는 `gh api graphql`로 조회해야 한다. 조회문은 `task` 스킬에 들어 있다.

**4. 지난 스프린트는 다른 목록에 있다.**
조회 결과의 `iterations`에는 진행 중·예정 스프린트만 있고, 끝난 것은 `completedIterations`에 있다. 목록이 비어 보여도 스프린트가 없는 것이 아니다.

**5. 스프린트 이름으로 찾으면 어긋난다.**
우리 보드에는 `Sprint 10`과 `sprint 12`처럼 표기가 섞여 있다. 이름이 아니라 조회한 ID로 다뤄야 한다. 처음부터 이름 규칙을 정해 두면 이 문제가 없다.

**6. 뷰 필터에 스프린트 이름을 적으면 스프린트가 바뀔 때마다 고쳐야 한다.**
`iteration:"Sprint 12"`처럼 적은 뷰는 다음 스프린트에서 빈 화면이 된다. `iteration:@current`를 쓰면 고칠 필요가 없다.

**7. `gh project item-edit`는 성공해도 아무것도 출력하지 않는다.**
세팅이 들어갔는지는 다시 조회해야 안다. 스킬에 확인 단계가 들어 있다.

**8. 이슈에 이미지를 API로 직접 올릴 수 없다.**
웹에서 끌어다 놓는 업로드는 API가 없다. 그래서 이미지 저장소를 따로 쓴다. 비공개 저장소 이미지는 링크가 `https://github.com/<주인>/<저장소>/blob/main/<경로>?raw=true` 형식이어야 로그인한 팀원에게 보인다.

**9. 이미지 저장소 초대를 수락하지 않은 팀원에게는 이미지가 깨져 보인다.**
등록한 사람 화면에서는 멀쩡해서 알아채기 어렵다. 6단계의 3번에서 다른 계정으로 확인한다.

**10. 디스코드 첨부 URL은 약 24시간 뒤 만료된다.**
디스코드에 올린 이미지 주소를 이슈에 붙이면 다음 날 깨진다.

**11. 디스코드 웹훅은 성공하면 본문 없이 `HTTP 204`를 돌려준다.**
응답이 비어 있어도 실패가 아니다.

**12. 작업일지를 Projects의 Status update에 올리는 방식은 맞지 않았다.**
사람별·스프린트별로 하나를 계속 고쳐 쓰는 구조는 같지만, 담는 곳을 라벨 붙인 이슈로 바꿨다. 이슈는 보드의 작업 중 칸에 카드로 계속 보인다.
